# AGENTS.md

The canonical agent guide for this repository. `CLAUDE.md` is a shim that points here; it also maps
the Claude-Code-specific tooling under `.claude/` (hooks, skills, subagents). How each part of the
pipeline and the app shell works is in [`ARCHITECTURE.md`](./ARCHITECTURE.md) — read the section for
the code you are changing; [Architecture reference](#architecture-reference) below indexes it.

## Start here

Blurt is a macOS dictation app powered by [AssemblyAI](https://www.assemblyai.com). Tap or hold a
trigger key, speak, and polished text is pasted into the focused app. Transcription is **one remote
AssemblyAI dictation API call**: the audio plus a request for the service's server-side LLM cleanup
rewrite (`config.llm_instruction`), so the text that comes back is already polished. (A recording
past the streaming route's 120 s cap is the one exception: it is sent again, whole, to the
buffered route — see [the over-cap fallback](./ARCHITECTURE.md#the-over-cap-fallback).) The user supplies their own
API key. The request's `stt_prompt` carries **two context signals, newline-joined oldest first: the
user's recent dictations, then the text immediately before the cursor**. The frontmost app, the
window title, the focused field's label, and the selected text are captured for local work (paste
spacing, the injector's window identity, the developer-mode log) and none of them go on the wire.
`stt_prompt` and `prompt` are the same field, so never send both. The user's key terms ride a second
field, `keyterms_prompt`, as a flat list of strings. See
[Contextual prompt and key terms](./ARCHITECTURE.md#contextual-prompt-and-key-terms).

Four reflexes before you touch anything:

1. **`scripts/check.sh` is the definition of green** — the same script CI runs. Off-Mac, only
   `scripts/check.sh --portable` is available and it is _not_ green in the CI sense. See
   [Verifying your work](#verifying-your-work).
2. **Read [Settled decisions](#settled-decisions--dont-reintroduce-these) before changing
   architecture.** Every entry was tried the other way and reverted; reintroducing one is the most
   likely way to make things worse.
3. **Neither app's Xcode project is committed** — `App/Blurt/project.yml` and
   `App/BlurtiOS/project.yml` are the only sources, and every script that builds runs
   `xcodegen generate` first. Edit the yml; never commit a generated `.xcodeproj`, `Info.plist` or
   `.entitlements`.
4. **No external SPM dependencies in the engine** (rule, guarded by `check.sh`); each app carries the
   local `BlurtEngine` package plus the remote packages `check.sh` allowlists for that app, pinned
   exactly — Sparkle (the updater) in the Mac app, KeyboardKit (the keyboard's engine: free core, a
   closed-source binary) in the iPhone app — and `check.sh` rejects any other, in any spec, and any
   float.

### The two layers

| Layer                  | What it is                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Sources/BlurtEngine/` | Swift package (`swift-tools-version:6.2`, `platforms: [.macOS(.v15), .iOS(.v18)]`) owning the pipeline. Pure logic behind protocol seams, no AppKit-shell deps, **no external SPM deps** — Foundation/Security/AVFoundation/CoreAudio plus toolchain modules like Synchronization and Observation (`APIKeyModel`, the one `@Observable` type both shells share), with AppKit types only at the seams. The macOS-only files (Accessibility reads, clipboard paste, CoreAudio route reads, TCC and code-signing helpers) are fenced behind `#if os(macOS)`; `check.yml`'s `ios-build` job builds it for the iOS simulator, inside the iPhone app's build, so a symbol that escapes its fence fails the PR. |
| `App/Blurt/`           | AppKit/SwiftUI shell (Xcode project generated by XcodeGen) that wires the engine to an overlay window, the main window, a Settings scene, a menu bar item, and the trigger key, running it on AssemblyAI through `BlurtAssemblyAI`. Its packages are the local `BlurtEngine` package and Sparkle, the updater (declared in `App/Blurt/project.yml`).                                                                                                                                                                                                                                                                                                                                                     |
| `App/BlurtiOS/`        | The iPhone app (SwiftUI) and the keyboard it embeds, generated by XcodeGen from its own `project.yml` and built by `check.yml`'s `ios-build` job. The app owns the engine's pipeline over an always-on capture; the keyboard is a remote control that inserts the words. Their logic is `BlurtiOSCore`, a framework apart from the UI the way the engine is apart from the Mac shell. `App/BlurtiOS/README.md` is its guide.                                                                                                                                                                                                                                                                             |

**The engine names no speech provider.** It talks to speech AI only through its provider seams —
`TranscriberProtocol` (dictation), `SpeechSynthesizing` (read-aloud's voice), `ChatCompleting` behind
`GatewayConnection` (every LLM client), and a `KeyValidation` check for `APIKeyModel` — and a host
hands it the conformers (`SpeechServices` bundles the read-aloud ones). `BlurtEngine` imports neither
of the package's other two libraries:

- **`AssemblyAI`** (`Sources/AssemblyAI/`) is the AssemblyAI SDK: the `HTTPTransport` seam and its
  streamed upload body, the dictation client (`DictationClient`, with the over-cap fallback, warm-up
  and latency logging), the dictation wire types and multipart framing, the streaming TTS client
  (`SpeechClient`), the LLM Gateway client (`GatewayChatClient`), the realtime and async clients,
  OAuth, `APIKeyValidator`, and `KeyTerms`. It holds no Blurt code (no prompts, styles, key storage,
  `User-Agent` or on-device text processing), so another speech project can use it on its own.
- **`BlurtAssemblyAI`** (`Sources/BlurtAssemblyAI/`) is the provider package that runs the engine on
  that SDK: `AssemblyAITranscriber` (Blurt's request policy — prompt, key terms, cleanup instruction,
  rewrite mode, which transcript is pasted), the TTS and LLM adapters (`SpeechServices.assemblyAI()`),
  `FileTranscriber`, the realtime glue, `APIKeyValidator.blurt()` and `APIKeyModel(keyStore:)`, and
  Sign in with AssemblyAI (`Account/`). Another provider (Deepgram, say) is a sibling package that
  conforms to the same seams; it can supply all of them or only some, beside this one.

All three are part of the same local package, so the dependency-free rule is unchanged.

The engine's dependency-free rule is a **rule**. The apps carry two remote packages between them —
Sparkle, the Mac app's in-place updater (see [Updates](./ARCHITECTURE.md#updates)), and KeyboardKit, the iPhone
keyboard's engine (see `App/BlurtiOS/README.md` → Dependencies) — each allowlisted by URL and spec
file in `check.sh`'s dependency guard and pinned to an exact version, and the rebindable dictation
trigger is home-grown (`CGEventTap` over a pure state machine), not a package.

For embedding or extending the engine's public API — seam contracts, error table, quick start —
see [`Sources/BlurtEngine/README.md`](./Sources/BlurtEngine/README.md). This file covers repo-wide
workflow and the _why_ behind the design; the engine's README covers the _what_ of the API surface.

**The iPhone's platform scope.** iOS lets a capture start only while the app is in front
(`'!rec'`, 561145187, otherwise), so the listening window opens on the keyboard's hop or the app's
switch and is carried between dictations by an `IdleMode`: the Picture in Picture keeper
(`PictureInPictureIdle`, a zero-height `AVSampleBufferDisplayLayer` that keeps the process
`UserInteractiveFocal`, so a press from another app starts capture with no hop and the orange dot is
off between dictations) or a held mic (`HeldIdle`). The idle layer is separable; the window
(`ListeningWindowMachine`), the keyboard contract (`BlurtShared+SessionContract.swift`, `CommandRouter`,
`PressHandshake`) and the capture path are the same under either. The simulator enforces none of
this, so a change under `App/BlurtiOS/BlurtiOS/Sources/{ListeningWindow,WindowedAudioSource,DictationCoordinator}*.swift`
or `App/BlurtiOS/BlurtiOSCore/{BlurtShared+SessionContract,KeyboardModel*}.swift` is verified on a phone with
`scripts/ios-device.sh` (install → launch → dictate from Messages → `pull` → `syslog --negative`),
not only by `ios-check.sh`. `App/BlurtiOS/README.md` ("Testing on a phone") is the protocol;
`App/BlurtiOS/DESIGN.md` ("The two processes, and every number") holds every number the contract uses.

## Verifying your work

```bash
scripts/bootstrap.sh                        # install local dev tools on a fresh Mac
swift test                                  # engine unit tests (Swift Testing, @Suite/@Test)
swift test --filter DictationSessionTests   # single suite
swift test --filter happyPath               # single test case by name

scripts/check.sh                            # full health check — the same script CI runs
scripts/check.sh --portable                 # platform-independent subset (no macOS toolchain)
scripts/check.sh --lint-only                # only the read-only checks, minutes not half an hour (CI's lint job)
scripts/dev-build.sh                        # signed Debug build + install to /Applications
scripts/ios-device.sh preflight             # a real iPhone: ready? then install → launch → pull → syslog --negative
```

### What `check.sh` runs

In order, on a Mac. Each optional linter prints `note: <tool> not installed; skipping` when absent —
**a skip is missing coverage, not a pass**; run `scripts/bootstrap.sh` rather than accepting one.

**The order is deliberate: everything source-only runs before anything that builds.** Steps 1–5 cost
seconds and need no toolchain state; steps 6–11 cost ten-plus minutes. Run the other way round — as
this script was until a rework audit of this repo's closed PRs — a compile error means the
cheap checks are never reached, so their findings arrive on the _next_ red run, one at a time. A
green run does identical total work either way; what changes is how much a red run tells you. Only
the two checks that genuinely need the build products stay behind them (step 12).

1. **Repo-integrity guards** — no external SPM dependencies in the engine, only allowlisted and
   exactly pinned ones in the apps; and sound-catalog integrity (every
   `SoundPackCatalog` voice has both cue files, no orphans, no duplicate or reserved ids). Both run
   in `--portable` too. The catalog and the audio are generated together — both into the app
   target, one as source and one as resources — so drift plays silence with nothing raising an
   error.

2. **Shell portability** (`scripts/check-portability.sh`) — GNU-only idioms in `scripts/*.sh` and
   `.claude/hooks/*.sh`. Those run against BSD userland on a Mac and on CI, and GNU userland in a
   Linux / web sandbox, and shellcheck reads both as correct shell — so `sed -i` without a suffix,
   `grep -P`, `readlink -f`, `stat -c` and friends are written green and ship red (PR #116's
   BSD-sed invocation). Runs in `--portable`, which is where the divergence gets introduced.
   Mark a false positive with a trailing `# portable-ok: <reason>`; `--self-test` asserts every rule
   still matches its own probe, because a pattern that stops matching looks exactly like a clean
   tree.
3. **`swift-format lint --strict`**, then `swiftlint lint --strict`. Both are source-only, so they
   sit here rather than after the build. `swiftlint analyze` and `periphery` are the two that need
   build products; they're step 12.
4. **actionlint** (workflow correctness — and, via shellcheck, the inline `run:` bash) **/ zizmor**
   (workflow _security_: template injection, overbroad `permissions:`, unpinned actions — it matters
   most for `release.yml`, which hands the Developer ID key to a runner) **/ prettier** (yml/yaml/md
   — the repo holds no html/css/xml since the Pages site moved to assemblyai.com/blurt) **/
   markdownlint-cli2 / shellcheck / shfmt --diff** (`scripts/*.sh` formatting, style from the `[*.sh]`
   block in `.editorconfig`) **/ jscpd** (copy/paste detection over the Swift, shell and Python,
   tests included; config in `.jscpd.json`, zero clones allowed — factor a repeated block into a
   helper or fixture). jscpd is pinned by the lockfile in `tools/jscpd` (`npm ci --prefix
tools/jscpd`), which `check.sh` prefers over any other copy, since its tokenizer decides what
   counts as a clone.
5. **The evals** (`evals/`, the repo's only Python): `ruff format --check`, `ruff check`, `mypy`,
   and pytest under coverage.py, gated at 95% line + branch coverage (`program.py`, the DSPy
   adapter, excepted). Config in `evals/pyproject.toml`; the tools are locked in `evals/uv.lock`
   (`uv sync --project evals --locked`). The suite needs no
   network, no API key, and nothing beyond pytest — the one test that needs DSPy skips itself when
   it is absent. Followed by **`release.test.sh`**, pure-bash unit tests for the release
   orchestrator's decision helpers.

   Everything above this line is the `--portable` subset. Everything below needs a macOS toolchain.

6. `swift test` with `-warnings-as-errors`, plus an engine **line-coverage gate** (≥ `MIN_COVERAGE`,
   88%, `Tests/` excluded — raise it as coverage grows; `check.sh` records why ~91% is the ceiling).
7. **ThreadSanitizer** and **AddressSanitizer** test passes.
8. **Project generation** — `xcodegen generate` writes `Blurt.xcodeproj` from `project.yml`
   (nothing generated is committed), as the first part of the app build below.
9. **App build** with codesigning skipped (warnings-as-errors via `SWIFT_TREAT_WARNINGS_AS_ERRORS` in
   `project.yml`, scoped to the app target so it doesn't collide with the `-suppress-warnings` Xcode
   applies to SPM deps).
10. **`scripts/uitest.sh`** — the XCUITest bundle, part of the required gate.
11. **`scripts/leaks.sh`** — whole-app leak check under the Darwin leak detector, failing only on
    leaks attributable to Blurt's own code. Like the UI suite it needs a GUI session (windowserver),
    which the `macos-26` runner provides.

    **Steps 10 and 11 run on CI only.** Both drive the real app: the XCUITest runner takes over
    keyboard focus and clicking, and the leak run cycles dictation through the key tap and pastes
    into whatever is frontmost — so a local `check.sh` would make the machine unusable for the
    minutes they last. Locally they're skipped with a note (and the closing `ok` line repeats it);
    opt in with `BLURT_INTEGRATION_TESTS=1 scripts/check.sh`, or run `scripts/uitest.sh` /
    `scripts/leaks.sh` directly. On CI they run in `check.yml`'s own `ui-tests` job (two runners,
    split by test class; `scripts/uitest.sh` takes the selection), in parallel with the rest: its `macos` job runs `check.sh` with `BLURT_INTEGRATION_TESTS=0`, the one
    opt-out, and the required `check` job fails unless `ui-tests` passed. Set it nowhere else —
    outside that pairing it is a green-looking bypass of the suite.

12. **`swiftlint analyze`** (unused imports and declarations — reads the compiler log the app build captured) and
    **`periphery scan --strict`** (unused declarations — runs its own xcodebuild + index). The only
    two checks that can't move earlier. Both are `scripts/mac-static.sh` steps; on CI the
    `mac-static` job runs them beside `macos`, which skips them (`BLURT_STATIC_CHECKS=0`, CI only).
13. **`scripts/ios-check.sh`** — the same gates for `App/BlurtiOS`: `BlurtiOSTests` with
    `BlurtiOSCore`'s coverage gate, then `swiftlint analyze` over that build's log and periphery
    over the iPhone project. Locally only, and only when an iPhone simulator on this Xcode's iOS
    runtime exists (`xcodebuild -downloadPlatform iOS`); otherwise skipped with a note in the
    closing `ok` line. On CI the `ios-build`, `ios-audits` and `ios-static` jobs run its steps
    between them, in parallel.

The phone is outside `check.sh`: a change under the iPhone's capture, window, coordinator or App
Group contract files is verified on a real iPhone with `scripts/ios-device.sh` — `preflight`,
`install`, `launch`, dictate, `pull <dir> --syslog`, then `syslog <dir>/device.logarchive --negative`,
the system predicate every run asserts (iOS never refused Blurt a recording started from the
background). `App/BlurtiOS/README.md` › Testing on a phone is the protocol; `check.sh` only lints
the script (shellcheck, shfmt, portability).

CI (`.github/workflows/check.yml`) installs all of these via Homebrew on `macos-26` and runs the same
script in its `macos` job — steps 10 and 11 in `ui-tests`, in parallel — so a clean local
`check.sh` matches CI by construction. The one status branch protection requires is the summary
job named `check`, which fails unless every gate below passed or was skipped by design. One more
job **is** gated, because
`check.sh` cannot cover it: **`ios-build`** compiles the engine for the iOS simulator, as part of
the iPhone app's build (which links the `BlurtEngine` and `BlurtAssemblyAI` products), which is the only
place a macOS-only symbol that escaped its `#if os(macOS)` fence gets caught — `swift test` builds
for the host, and every other job runs on a Mac. With its siblings **`ios-audits`** and
**`ios-static`** it then runs **`scripts/ios-check.sh`**'s steps in parallel, which hold
the iPhone code to the bar the engine and the Mac shell meet in `check.sh`: `BlurtiOSTests` with
warnings as errors and a **line-coverage gate** on `BlurtiOSCore`, the iPhone code's logic
(≥ `MIN_IOS_COVERAGE` in `scripts/ios-test.sh`, the engine's 88%; raise it as coverage grows), in
`ios-build`; the accessibility audits at both text sizes in `ios-audits` (two runners, split by
test); **`swiftlint analyze`** over a from-scratch
build's log and **periphery** over the iPhone project in `ios-static`; `check.sh`'s swift-format, `swiftlint lint` and invariants already read every Swift file
there. In the sibling
**`ios-sanitizers`** job, one runner per sanitizer — **ThreadSanitizer** and **AddressSanitizer**
passes run the same tests. `codeql.yml`'s Swift analysis builds the iPhone app as well as the Mac
one, so both are in its database. `check` fails unless `lint`, `macos`, `ui-tests` and all of
them are green: `lint` may be skipped only for a docs-only change, and the others (with the
ungated `compile` and `format-patch`) also for an evals-only one — nothing but files under `evals/` other than JSON, which no Swift build or
test reads (`evals/**/*.json` still counts as Swift: `PlannerEvalTests` reads
`evals/command-planner/cases.json`).

- **`lint`** — `scripts/check.sh --lint-only`: every read-only check `check` runs before the build
  (swift-format, `swiftlint lint`, jscpd, design-sync, the invariants, the workflow, shell and
  Markdown linters, ruff, mypy, pytest + coverage), then stop. `check` runs the same checks first but by design keeps
  going through the build, the tests, the UI suite and periphery before reporting, so in the month
  before this job existed every red `check` run was one of these checks surfacing 30–39 minutes in;
  `lint` reports them in minutes. `check` still runs them, so it remains a complete answer on its
  own. For an evals-only change it is the only job that runs.

Two more sibling jobs exist purely to shorten the loop for whoever is editing Swift without a
toolchain, and **neither is a required check** — both can only go red where `check` would too:

- **`compile`** — `swift build --build-tests -Xswiftc -warnings-as-errors` and nothing else. A test
  target that doesn't build is the most common way a PR here goes red, and this reports it in ~2
  minutes instead of ~11.
- **`format-patch`** — runs `swift-format` for real and publishes the resulting `git diff` as a job
  summary and a `swift-format-patch` artifact. `check` can only tell you _that_ a file is
  misformatted; this hands you the exact reflow, which matters when there's no formatter on the
  machine you're editing from. Advisory and read-only: it never fails the build and never pushes.

There is deliberately **no per-PR installable build**. One existed (a `dev-build` job plus
`pr-dev-build.yml` posting the artifact link) and was removed: a hosted PR runner can reach no
signing key — the Apple Development cert is per-developer, and the Developer ID key is scoped to
`release.yml`'s protected environment — so the artifact was ad-hoc signed, which pins the cdhash
into its designated requirement and makes every rebuild a different app to `tccd`. Reviewers hit a
Blurt row switched on and still denied, and the machinery to work around it (a self-heal path, a
`tccutil` line in the PR comment, a fork-only `workflow_run` job to post it at all) outweighed what
it bought. Don't reintroduce it without solving the signing problem first. Reviewers build locally:
`scripts/dev-build.sh`.

Reporting rules: exit 0 with no `error:` lines is green. Anything else is not — quote the failing
step verbatim, don't soften it, fix it, then re-run the **full** script (a `swift test --filter` pass
is not green).

### Regenerating and installing the app

```bash
cd App/Blurt && xcodegen generate        # generate Blurt.xcodeproj from project.yml
xcodebuild -project App/Blurt/Blurt.xcodeproj \
  -scheme Blurt -configuration Debug \
  -derivedDataPath /tmp/blurt-build build
```

The xcodebuild post-build script (`App/Blurt/project.yml`) copies the bundle to
`/Applications/Blurt Dev.app` (or `~/Applications/` fallback) and re-signs it with the **Apple
Development** cert (login keychain) under a team-based designated requirement — never the Developer
ID release key, which lives in a locked keychain used only by releases. This is deliberate: TCC
refuses to register apps living in DerivedData or `/tmp`, so Accessibility/Input-Monitoring toggles
never appear unless the app has a stable install path. **Don't bypass it.**

**Debug builds are a separate app.** Every debug configuration builds as `dev.alex.blurt.dev` /
"Blurt Dev"; only `Release` is `dev.alex.blurt` / "Blurt" (`PRODUCT_BUNDLE_IDENTIFIER` and
`BLURT_APP_NAME` in `project.yml`, which also feed `CFBundleName`/`CFBundleDisplayName` and the
install path). `PRODUCT_NAME` stays `Blurt` in both — it names the executable and the product in
`BUILT_PRODUCTS_DIR`, which every script is written against. The split is what stops a dev build
from inheriting a released Blurt's TCC rows while failing the requirement stored with them, and it
means both can be installed and run side by side. The debug id is the _default_ and `Release` opts
in to the shipping one, so a configuration added later can't accidentally ship under it.

**The Keychain is the one store the id split doesn't separate for you.** Keychain items are per
_login keychain_, not per app, so both builds resolved the same `blurt` generic-password item however
different their bundle ids were — a dev build read the shipping app's API key, could overwrite it,
and (once Settings grew a Reset) could delete it. `HostIdentity.blurtDev` gives the debug build its
own `blurt-dev` item, and `BlurtApp.init` picks between the two identities by the **running bundle
id** — which follows `PRODUCT_BUNDLE_IDENTIFIER`, so a new configuration inherits the dev identity
rather than reaching for the shipping key because someone forgot a `#if DEBUG`. Only that one field
differs: the log subsystem stays shared (the documented `log show` predicates have to work whichever
build is running) and so does the defaults prefix (defaults are per-app already). The cost is one
extra trip through the wizard the first time you run a dev build after this landed.

`scripts/dev-build.sh` wraps that for everyday local dev — it runs the **signed** `Debug-Local` build
(so the install step actually fires, unlike `check.sh`, which disables codesigning for CI) and pipes
through `xcbeautify` when present. [`CONTRIBUTING.md`](./CONTRIBUTING.md) is the setup guide for
someone starting from a clean Mac, including the ad-hoc build for contributors with no signing
certificate.

### The Accessibility grant and signing identity

TCC pins an Accessibility grant to the app's **designated requirement**, and re-checks the running
binary against the requirement it stored. When what that requirement pins changes, the grant is
orphaned in the worst possible way: the Blurt row stays in System Settings, switched on, while
`AXIsProcessTrusted()` keeps returning false — so the wizard's Accessibility step can never be
satisfied and toggling the row does nothing. Two defences, in this order:

- **Separate bundle ids** stop the everyday case. A release carries codesign's _default_ Developer
  ID requirement (leaf CN + marker OIDs) and a dev build an explicit team-based one, so the two
  never satisfy each other — sharing a bundle id meant installing `dev-build.sh` over a release
  inherited its rows and failed its requirement. `dev.alex.blurt` vs `dev.alex.blurt.dev` makes them
  two apps with two sets of rows, and neither can strand the other.
- **A launch-time self-heal** covers what a split id can't: a **re-issued Developer ID certificate**
  ([`RELEASE.md`](./RELEASE.md)'s rotation procedure) changes the leaf that a release's default
  requirement names, orphaning the grant of every installed user at once. Nothing at signing time
  can pre-empt that — the requirement a shipped copy handed to `tccd` was written before the
  rotation existed. (The dev side is already immune: the post-build script pins
  `leaf[subject.OU]`, which survives the yearly Apple Development cert rotation.)

`AppDelegate.runAccessibilityGrantMigration` is the self-heal. It compares `SigningIdentity.current()`
— the app's **designated requirement**, serialized and namespaced (`dr:<requirement>`) — against the
identity recorded in `accessibility.lastSigningTeam`; if it changed and the app is untrusted, it runs
`tccutil reset Accessibility` on **the running bundle id** (never `HostIdentity.current.subsystem`, which
would have a dev build clearing the release's grant) so the wizard's normal grant flow captures a
matching requirement, and records the new identity only when the reset succeeded.
`SigningIdentityMigration` is the pure decision; `SigningIdentity` reads the requirement (the thin
`Security` adapter) and `PermissionsReset` runs the `tccutil` call — the same adapter the Settings
window's reset button sweeps every grant through.

Recording the requirement itself, rather than a proxy for it, is the point: this used to record the
**Team ID**, which is stable across exactly the collision above (release and dev builds share team
`B2VQF7Q2QY`), so switching builds read as "unchanged", no reset ran, and the wizard's Accessibility
step became unpassable. The requirement string moves when and only when `tccd`'s stored copy stops
matching.

`SigningIdentity.current()` answers **nil for ad-hoc and unsigned code**, which the migration reads
as "no action". Ad-hoc signatures pin a cdhash, so honouring them would have every `uitest.sh` /
`check.sh` run — each a throwaway ad-hoc binary under the debug bundle id — wiping the developer's
own Blurt Dev grant. This used to be an `includingAdHoc:` parameter the call site had to pass
correctly (`false` under `#if UITEST_HOOKS`); it is a property of the function now, which is both
one fewer flag and one fewer way to get it wrong. The team identifier is the probe for "is this
ad-hoc" — present exactly when the signature isn't — never the value recorded.

### Working without a macOS toolchain (remote / Linux sandboxes)

This is a macOS-only project (AppKit + AVFoundation, and the engine imports AVFoundation), so on
Linux or a web sandbox you **cannot build, test, or run it** — `swift test`, `xcodebuild` and
`xcodegen` need the Apple SDK. What needs no SDK does run: `scripts/install-linux-swift.sh` (the web
`SessionStart` hook runs it) installs the Linux Swift 6.2 toolchain, so `swift-format`, SourceKit
(for SwiftLint) and `swift` scripts are available; `CLAUDE.md` › "The Swift toolchain on Linux" has
the table.

- **You can**: read and edit Swift, reason about the pipeline, adjust the transcription prompt and
  docs, and write tests for later verification.
- **You must not**: run (or claim to have run) the full `scripts/check.sh`, or assert that a build or
  test passed. Say plainly that verification happens on a Mac — CI runs the full `check.sh` on
  `macos-26` and is the authority on green.
- **The portable gate**: `scripts/check.sh --portable` runs the repo-integrity guards
  (dependencies, sound catalog, site, shell portability), then actionlint, zizmor, prettier, xmllint,
  markdownlint, shellcheck, shfmt, jscpd, ruff (lint + format check), mypy and pytest (with its
  95% coverage gate) over the evals, and
  `release.test.sh`, plus — when the Linux toolchain and SwiftLint are installed —
  `swift-format lint --strict`, `swiftlint lint --strict` and `design-sync.sh --check`. It fully
  verifies docs, site, scripts, eval, and workflow changes, and Swift formatting and lint; it skips
  the build, the tests and the static analysis, and its closing line says so. **Run it before every
  push, Swift changes included** (the `push-gate` hook does): jscpd, the invariants, SwiftLint,
  swift-format and the shell, workflow and Markdown linters all catch real CI failures from here.
  So do three Swift checks that need no toolchain at all:
  `scripts/check-swift-size.sh` counts SwiftLint's `file_length` (400) and `type_body_length`
  (~250) budgets and notes files within 20 lines of either, where a parallel PR can tip the merge
  over; `scripts/check-test-clock.sh` fails a fixed sleep or real clock in a test that doesn't
  say why (step a `TestClock` or wait for the event; `// wall-clock-ok: <reason>` where real time
  is the point); and `scripts/check-swift-lint-lite.sh` matches the opt-in SwiftLint and swift-format
  rules text can see (`modifier_order`'s `nonisolated public`, `no_empty_block`, `NoBlockComments`,
  swift-format's `catch  where` spacing). **After merging `main` into a branch, run it again**: two PRs that
  each fit a size budget merge into one that doesn't (#363, #378), and a merge fires no edit hook.
- **Rules that cost a CI run**, each of which cost a recent PR one — write Swift to them up front.
  With the Linux toolchain and SwiftLint installed, the push gate now catches all of them but
  `MemberImportVisibility` (a compiler check):
  - `variable_shadowing` / `shadowing`: don't rebind a parameter or outer name with `let`
    (`let entries = … entries` → `let written`), and don't redeclare a name a helper already binds
    (#410, #416).
  - `one_declaration_per_file`: a test file's helper types nest inside its suite, not beside it
    (#423).
  - `type_contents_order`: type (`static`) methods sit together, ahead of instance methods (#426).
  - `multiline_function_chains`: bind an intermediate (`let window = …`) rather than wrapping a
    chain across lines (#410).
  - `MemberImportVisibility` (the engine's strict compiler settings): import every module whose
    members a file uses — `Foundation` beside `Testing`, `Dispatch`, `CoreFoundation` (#392, #423).
  - swift-format: once a call wraps, every argument goes on its own line, table rows included
    (#409); empty closures carry a `//` line comment on its own line, never `/* */` (#414).
  - jscpd: a second test that repeats another's setup gets a shared helper on the first push
    (#384, #420, #422) — `--portable` runs it, so the push is where it is caught, not CI.
- **Splitting a file**: give each new file only the imports it uses — `swiftlint analyze`'s
  `unused_import` (CI only) flagged 86 copied headers in #392 — and import a type from the module
  that declares it (`CGFloat` from CoreFoundation, `DispatchQueue` from Dispatch).
- **What only CI can tell you**: the build and every test, the compiler's checks
  (`MemberImportVisibility`, strict concurrency), `swiftlint analyze` and periphery (a property
  that is assigned but never read is the usual catch), and the iOS typecheck — plus swift-format,
  SwiftLint and design-sync if the `SessionStart` hook couldn't install them (its preflight line
  says so). Expect `lint` to answer the last group in minutes rather than `check` in forty.
- **Push once per batch of fixes**: every push cancels the `check.yml` run in progress and restarts
  its ~37 minutes. When a run goes red, fix every failure it names (and apply the
  `swift-format-patch` artifact rather than guessing at a reflow) before pushing again.
- **The loop for Swift changes**: commit, push, open or update the PR, then watch `check.yml`
  (subscribe to PR activity where available) and fix failures as CI reports them — rather than
  stopping at "verify on a Mac". **The PR is not optional**: `check.yml` triggers on
  `pull_request` to `main`, `merge_group` and a manual dispatch only, so pushing a feature branch runs _no_ CI
  and leaves Swift changes wholly unverified. A push is not a check.
- **Diff against `origin/main`, not `main`**: a fresh remote clone checks out only the working
  branch, so the local `main` ref lags behind the real default branch. `git diff main...HEAD` there
  reports every commit merged since that stale ref as if it were yours.

In Claude Code on the web, a `SessionStart` hook installs the portable linters automatically; see
[`CLAUDE.md`](./CLAUDE.md).

## Conventions

- **Indent: 2 spaces** (`.editorconfig`) — Swift, Obj-C, C/C++.
- **Formatting authority is Apple's `swift-format`** (bundled with Xcode 16+); config is
  `.swift-format` (120-col lines, 2-space indent). `check.sh` runs `swift-format lint --strict`.
- **SwiftLint** (`.swiftlint.yml`) runs every opt-in rule it has (`opt_in_rules: [all]`, plus every
  analyzer rule but `explicit_self`) with `--strict`, so warnings are failures. The two don't fight:
  a layout rule whose fixes swift-format undoes is disabled, as is any rule that contradicts another
  or a convention here, each with its reason in `.swiftlint.yml`. Fix a finding in code; a
  `swiftlint:disable:next` with a reason is for the rare fix that would change behaviour.
- **Force-unwraps (`!`), implicitly-unwrapped optionals, and `unowned` captures are banned repo-wide**
  (opt-in rules in `.swiftlint.yml`). Spell constant URLs `URL(staticString:)`
  (`Sources/BlurtEngine/URL+StaticString.swift`) and unwrap in tests with `try #require(...)`.
- **Swift 6 strict concurrency**: actors own state (`DictationSession`, `KeyInjector`, `MicCapture`);
  `@MainActor` guards UI/coordinator state (`AppCoordinator`, `WizardController`, overlay). The
  stateless API clients (`AssemblyAITranscriber`, the SDK's `DictationClient`) stay `Sendable`
  structs. `static var` without isolation fails the build under `-warnings-as-errors` — prefer
  `static let`.
- **Unit tests use Swift Testing** (`@Suite`/`@Test`/`#expect`), not XCTest. The XCUITest bundle is
  the one exception (XCTest, because XCUIAutomation requires it).
- **A store setter with no production caller gets deleted.** The exception is a value that's
  _encoded_ on write (`TriggerKeyStore`'s keycode, `SoundPackStore`'s id, `StyleProfileStore`'s JSON
  profile list): there, give the setter a production caller instead — see `KeysSettingsTab`, where assigning the raw `@AppStorage` slot
  directly left the setter test-only, so a change to the encoding would have kept `swift test` green
  while the picker silently wrote the old form. For a plain `Bool` there is nothing to encode, so the
  Settings toggle writing the slot through `@AppStorage` is the whole story and the store stays
  read-only (`DeveloperModeStore`, `EnhancedTranscriptsStore`). Either way, no setter is left in the
  engine that only tests exercise.
- **Pure projections over shell logic**: phase→UI mapping (`OverlayUIState`, `MenuBarStatus`),
  chime edges (`RecordingCueGate`), geometry (`OverlayPlacement`, `MeterBarGeometry`), history
  (`RecentDictations`), alert wording (`APIKeySubmission.FailureReport`, `InstallReset.AlertContent`),
  credential display (`APIKeyDisplay`) and setup policy (`SetupReadiness`) live in the engine as value
  types so they're unit-testable; the AppKit side just renders whatever they resolve to. Keep new logic
  on that side of the line — the shell has no test target, so wording and classification assembled at
  a SwiftUI/`NSAlert` call site is covered by nothing.
- **Docs**: prose lines are wrapped ~100 cols in this file; prettier owns Markdown formatting
  (`proseWrap: preserve`, so wrapping is yours to keep tidy) and `MD013` is off.

## Tests

**Engine unit tests** — `Tests/BlurtEngineTests/`, Swift Testing (`@Suite`/`@Test`/`#expect`). All
three seams have stubs in `Stubs/` (`StubMicCapture`, `StubTranscriber`, `StubInjector`, plus
`FakeHTTPTransport` for transport-level transcriber tests). Every session a test builds passes
`seams:` — `.offline` for the suites that only need the window server, the Accessibility API and the
real log kept out of it, or `testSeams(field:frontmost:log:)` to drive and then assert the captured
context and what was logged. A test must never reach a production global: `swift test` on a machine
with developer mode switched on used to append its fixtures to the user's own `dictations.jsonl`,
which is the same rule as "don't touch the real Keychain in tests". Retain-cycle leaks are gated by
weak-reference assertions in `MemoryLeakTests.swift` (`expectNoLeak`) — LeakSanitizer is unsupported
on Darwin, so AddressSanitizer catches memory _corruption_ but not leaks; `scripts/leaks.sh` covers
the whole app under the Darwin leak detector.

**Control Your Mac** is tested at every layer, the way other computer-use projects (Peekaboo,
OpenAdapt, browser-use) split theirs: fast and offline on every run, live only when asked — which CI asks for
the live performer alone. The
suites that drive this Mac's real apps share one gate (`.drivesThisMac`, in `Stubs/MacDriver.swift`:
the variable that asks for it plus Accessibility trust) and one tag, so a normal run reports them
skipped.

- **Policy and decisions, every run.** The step parse and its checks — an element's kind, a
  destructive label, a looping step, all refused before any step runs — name matching, the snapshot
  walk, and the router with a stub planner and performer. What the real performer decides is
  covered too, apart from the Accessibility calls it makes: `ElementActions` holds when a press falls
  back to a click, when a focused field is selected, the menu walk and the pointer's round trip, each
  driven in `ElementActionsTests` with fake reads and writes. The `SystemVoiceCommandPerformer*`
  shell files stay outside the coverage gate.
- **Recorded screens, every run.** `Tests/ScreenTrees/` holds real apps' windows — 1Password, Chrome,
  Finder, Mail, Obsidian, Safari, Slack and VS Code — recorded from a Mac by `ScreenTreeRecorder` (`BLURT_RECORD_TREE=1`,
  `BLURT_RECORD_TREE_ONLY=Slack,Mail` for some) with **every string swapped for fake text** ("Lorem 12"), but
  a short list of generic interface words (Inbox, Search, Home). `RecordedScreenTests` replays them
  through the screen read's own code (`ScreenRead`, which the live read calls with real Accessibility
  nodes through the `ScreenNode` protocol), so what a window lists is checked with no app running: 1Password's
  value-named items, VS Code's page past its share, Finder's search button, Slack's sidebar rows, a browser page never crowded out by its tab strip. A
  re-recording is held to its anonymity on every run: `noRealText` refuses any string that isn't
  fake or on the keep list, anything shaped like an address, path or phone number, and any key the
  recorder doesn't write. The list of recordings is `RecordedNode.recordings`, shared by the recorder
  and the tests, and `everyRecordingOnDisk` holds the folder to it.
- **Paste situations, every run.** `Tests/PasteFixtures/pastes.json` holds where a dictation lands in
  real apps — Google Docs' page, Chrome's and Safari's address bars, VS Code's editor and command
  palette, the Claude app's prompt, Slack's composer, Obsidian, 1Password's unlock field, Muse's reply box, Messages, Notes,
  TextEdit, Terminal, System Settings' search, and two with nowhere to paste (a Finder window,
  Calculator) — as the facts the paste decision reads (`PasteFacts`: role, subrole, settable value,
  insertion point, inside a web area, the app's bundle id and Electron-ness; never text), each with the
  outcome that's right there. `PasteFixtureTests` replays them through `PasteTarget.pastes`, the
  decision `KeyInjector` makes. `PasteFixtureRecorder` (`BLURT_RECORD_PASTE=1`,
  `BLURT_RECORD_PASTE_ONLY=a,b`) records them by driving each app's focus there, never typing.
- **The reply parser, fuzzed, every run.** `ReplyParserFuzzTests` throws 20,000 seeded replies — well
  formed, missing fields, wrong types, cut short, wrapped in prose — and 5,000 byte strings at
  `VoiceCommandStep.steps`: each must be refused with a `VoiceCommandError` or parse to a plan that keeps
  every rule (listed elements only, no destructive chord or label, allowed schemes, typed-text and menu
  limits, no loop). Seeded, so a failure replays.
- **The live performer, `BLURT_LIVE_AX_TESTS=1`.** `LivePerformerTests` launches
  `Tests/CommandFixture` (a SwiftPM executable the test target depends on, never a product): a window
  with one of each control. It runs real steps against that window and judges each one by the state
  the fixture writes to a JSON file — the presses it saw, the slider's value, the selected row, the
  field's selection — never a screenshot. It needs Accessibility trust for the process running it,
  and it stops before any step unless the fixture is the app in front, so input meant for it can't
  land elsewhere. A process spawned by the test can't take the front by itself, so the test process
  registers as an accessory app and activates the fixture. It pins a native app's press as trusted:
  Reply, which visibly answers, and Send, which changes nothing, are each pressed once.
  It runs on CI too, in `check.yml`'s required `live-tests` job, with the live-audio suites
  (`BLURT_LIVE_AUDIO_TESTS=1`, on a loopback input fed white noise): a throwaway runner, whose image already
  grants the runner's processes Accessibility and Microphone trust. That job fails unless every
  suite reports it _passed_, since a missing gate skips a suite and `swift test` still exits 0.
- **The planner, `BLURT_PLANNER_EVAL=1`.** `PlannerEvalTests` scores the real planner — instruction,
  schema, retry, parser — on `evals/command-planner/cases.json`, and fails below the corpus's
  `passFloor`. It costs paid gateway calls, and one run is noise (the model varies even at
  temperature 0), so it runs each case three times. The corpus's shape is checked on every run. Its
  README says how to read a result and how to draft cases from `commands.jsonl`. Cases can also run over the
  recorded screens — written with `"screen"`, or generated from each recording
  (`BLURT_PLANNER_EVAL_SET=corpus|screens|all`) — so the planner is scored on full 150-element windows,
  not only the handful of elements a written case lists. The corpus, drafted from real logs, is
  scanned every run for anything personal and for keys `Case` doesn't decode.
- **The app's pipeline, XCUITest.** `CommandPipelineUITests` (in `App/Blurt/BlurtUITests`) drives the
  real app under the UI-test harness with a fake planner, performer and rewriter
  (`UITestPlanner.swift`, `UITestPerformer.swift`, `UITestRewriter.swift`): a command planned, performed and done; the pill held while one
  works; a typed step pasted; a complaint noted; overheard speech refused; a rewrite pasted. Its
  README says how to run it.

**Mutation testing** — `scripts/mutate.sh`, opt-in and **not** part of `check.sh`. It flips one
operator in a source file, re-runs the suite, and reports whether anything noticed. Reach for it
instead of chasing the coverage number: the engine is near its line-coverage ceiling (the remainder is
Accessibility/TCC/CGEvent code no CI process can run), so the useful question is no longer "did this
line execute?" but "is it _asserted_?" — a surviving mutant is a behaviour change no test objected
to. Its default target list is the files already at or near 100% coverage, which is exactly where the
coverage number has nothing left to say. It stays out of `check.sh` deliberately: a run is minutes,
and survivors need judgement (an _equivalent_ mutant cannot change behaviour, so no test can catch
it), and a required gate that reports unactionable failures is one people learn to skip. To run the whole set without tying
up a Mac, start the `mutate` workflow (`.github/workflows/mutate.yml`) from the Actions tab: it splits
the mutants across eight macOS runners (`--shard K/N`), and its `report` job lists every survivor and
goes red while any remain. It never runs on pull requests.

**Swift Testing traps that CI has caught more than once.** Nothing here can be typechecked without a
macOS toolchain, so when you're writing tests from a Linux / web sandbox these are the ones that cost
a red run. Check them by eye before pushing:

- **`#expect` takes an autoclosure, so it cannot call a `mutating` method.** The value is captured
  immutably and the compiler rejects the call. Bind to a `var`, mutate, then assert the result. (Cost
  a round trip on both #118 and #122.)
- **`#expect` around a `rethrows` call with a throwing argument needs `try`.**
  `#expect(hex.allSatisfy(\.isHexDigit))` is the exact form that failed — `allSatisfy` is `rethrows`,
  the key path can throw, and the macro expansion surfaces it as "call can throw, but it is not
  marked with `try`". Write `try #expect(…)`, or hoist the computation above the assertion.
- **A new test file needs its own imports.** `pid_t`, `Data`, `URL` and friends come from Foundation;
  a file that only imports `Testing` and `BlurtEngine` won't see them (#122).
- **Splitting a type across files breaks `private(set)`.** The other half is a different file, so it
  needs `internal(set)` — and `@testable import` reaches internal, never private (#122, #80).

The `compile` CI job exists for exactly this class: it reports a broken test build in ~2 minutes
rather than behind the full suite.

**Integration tests (XCUITest)** — `App/Blurt/BlurtUITests/`, a `bundle.ui-testing` target declared
in `project.yml` and wired into the `Blurt` scheme's test action, so it runs via `xcodebuild test`.
`scripts/uitest.sh` drives it, `check.yml`'s `ui-tests` job runs that as part of the required gate,
and `scripts/check.sh` invokes it too — but **on CI only**: it needs a GUI session and commandeers it, so a local `check.sh` skips it (as it does
the leak scan) unless `BLURT_INTEGRATION_TESTS=1`. Run `scripts/uitest.sh` directly to iterate on the
suite; CI is the authority on whether it passes.

The suite drives the **real app** against deterministic, offline doubles rather than mocking the UI.
A `-BlurtUITest` launch argument flips on a Debug-only harness (`App/Blurt/Blurt/UITest*.swift`,
all `#if UITEST_HOOKS` — defined for the Debug config, so `scripts/dev-build.sh` can strip it) that:

- swaps the mic / transcriber / injector for stubs and the Keychain key store for an in-memory one
  (no microphone, network, Accessibility, or real Keychain — injected via `DictationComponents` /
  `APIKeyGateway`, the seams added to `AppCoordinator`), and
- presents a harness window with controls that drive the **same** `DictationSession` the hotkey would
  (the lone-modifier `CGEventTap` can't be synthesized in XCUITest and needs an Accessibility-trusted
  process), plus read-outs for the live pipeline phase and the text the injector "pasted".

So the four areas map to: **settings** → the real Settings window's controls (addressed by
`accessibilityIdentifier`); **menu bar** → the live `MenuBarExtra` status item and its menu;
**recording audio** + **pasting into an app** → the harness drives press/release and asserts the
canned transcript reaches the injector. A `-BlurtUITestReady` flag forces the fully-configured state
so the main window renders `ReadyView` (the test host can't grant real TCC permissions). The
CGEventTap→gate wiring stays covered by the engine unit tests (`DictationKeyGateTests`,
`HotkeyRaceTests`); the hardware trigger and a real ⌘V paste remain manual-only.

Identifiers, window titles, the launch arguments, and the offline sentinel keys all live in
**`App/Blurt/Shared/UITestIdentifiers.swift`**, which `project.yml` lists under _both_ targets'
`sources` (the test bundle can't import the app module). Add or rename a UI-test-facing string
**there** — don't reintroduce mirrored copies in `BlurtUITests/`.

**After editing `project.yml` there is nothing to regenerate and commit**: the project is generated
by every script that builds, so the yml edit is the whole change.

## Releasing

Releases run entirely in GitHub Actions, so they can be driven from a browser or a chat session with
no terminal, and without permission to dispatch a workflow. Start `release-bump` by pushing a marker
branch at main — `git push origin main:refs/heads/release/v0.1.37`, which names the version and
carries nothing else — or by dispatching it (that path also takes an empty version and derives the
next patch). It bumps `project.yml`, regenerates the project on `macos-26`, and leaves the bump on
`release/vX.Y.Z`; on the marker path it first checks the branch is an ancestor of `main`, so pushing
a branch can't smuggle content under a bot-authored commit. Then open and merge that PR. **Merging it starts
`release`** — `release.yml` also triggers on a push to `main` that changes `project.yml`, and its
`resolve` job releases only when the version actually changed and no `vX.Y.Z` tag exists yet, so a
project.yml edit that isn't a bump skips the build. Dispatching `release` by hand still works and is
what re-runs a failed build, `republish`, and the non-`main` dry run. The bump workflow deliberately
does not open the PR — a PR created by `GITHUB_TOKEN` never triggers `check`, so it could never
merge; opening it from outside Actions works fine, and the same rule applies to the merge (an Actions
merge with `GITHUB_TOKEN` raises no `push` event, so it would not start `release`). The publish job
then parks on the `release-publish` environment until a human approves — that approval is the ship
gate, so download and test the DMG from the build job's artifacts first. Nothing is rebuilt after
approval.

**If you are an agent: never approve that deployment yourself**, even though the API allows it and
you may have the permission. The gate exists so a person confirms the real artifact works before it
reaches users; approving a build you started is not a gate. This rule is repeated in
`.claude/skills/release` and lives here too because that skill is `disable-model-invocation: true` —
it does _not_ load when someone just says "release", which is exactly when the rule matters.
Dispatching `release-bump` with an empty version takes the next patch, resolved by `default_target` /
`decide_run` in `scripts/release-lib.sh` (unit-tested by `release.test.sh`, so it is verifiable off a
Mac); the marker-branch path has no such default, because a branch that named no version would be
asking the workflow to guess what its own name meant. There is no local orchestrator script — the workflows are the only path, so there is nothing to
drift out of sync with them.

Signing-key custody (a base64 `.p12` secret imported into an ephemeral keychain, never a persistent
one), the required environments and secrets, certificate/notary rotation, and the roll-forward-only
policy for a bad release are documented in [`RELEASE.md`](./RELEASE.md).
